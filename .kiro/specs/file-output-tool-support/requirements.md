# Requirements Document: Поддержка инструмента записи файлов для адаптеров

## Introduction

Система workflow-оркестратора использует CLI-адаптеры для взаимодействия с различными LLM моделями. При генерации больших текстов (например, документов требований) возникает проблема обрезания вывода при чтении из stdout. Для Gemini уже реализовано решение через разрешение инструмента `write_file`, которое позволяет модели записывать результат напрямую в файл. Необходимо реализовать аналогичный подход для Codex и сделать это общим решением для всех адаптеров.

## Glossary

- **Adapter**: Компонент системы, обеспечивающий взаимодействие с конкретной LLM через CLI
- **Codex**: CLI-утилита для взаимодействия с моделями OpenAI
- **Gemini**: CLI-утилита для взаимодействия с моделями Google
- **write_file**: Инструмент, позволяющий модели записывать контент в файл
- **stdout**: Стандартный поток вывода процесса
- **Workflow**: Последовательность шагов для выполнения задачи
- **Artifact**: Выходной файл, создаваемый на шаге workflow

## Requirements

### Requirement 1: Поддержка инструмента записи файлов в Codex адаптере

**User Story:** Как пользователь системы, я хочу чтобы Codex адаптер поддерживал запись результатов в файлы через инструмент write_file, чтобы избежать обрезания больших текстов при чтении из stdout.

#### Acceptance Criteria

1. WHEN в конфигурации шага указан outputs с путем к файлу, THE Codex_Adapter SHALL добавить флаг --allowed-tools write_file
2. WHEN в конфигурации шага указан outputs с путем к файлу, THE Codex_Adapter SHALL добавить флаг --yolo для автоподтверждения
3. WHEN в конфигурации шага указан outputs с путем к файлу, THE Codex_Adapter SHALL добавить флаг --output-last-message с путем к файлу
4. WHEN модель записывает результат в файл через write_file, THE Codex_Adapter SHALL прочитать содержимое файла и вернуть его как результат
5. IF файл не был создан моделью, THEN THE Codex_Adapter SHALL использовать stdout как источник результата
6. WHEN используется флаг --output-last-message, THE Codex_Adapter SHALL ожидать завершения записи файла перед чтением

### Requirement 2: Автоматическое добавление инструкции записи в файл

**User Story:** Как разработчик workflow, я хочу чтобы система автоматически добавляла инструкцию записи в файл в промпт, чтобы не дублировать эту информацию в каждом шаге.

#### Acceptance Criteria

1. WHEN в конфигурации шага указан outputs с путем к файлу, THE Adapter SHALL автоматически добавить инструкцию записи в конец промпта
2. WHEN добавляется инструкция записи, THE Adapter SHALL использовать формат "CRITICAL: If write_file tool is available, use it to save your response to file path: <путь>. If write_file tool is not available, output your response to console."
3. WHEN путь к файлу относительный, THE Adapter SHALL указать что путь относительный к текущей рабочей директории
4. WHEN инструкция добавлена, THE Adapter SHALL сохранить путь к файлу для последующего чтения результата
5. IF в конфигурации шага не указан outputs, THEN THE Adapter SHALL не добавлять инструкцию записи в файл

### Requirement 3: Унификация подхода для всех адаптеров

**User Story:** Как разработчик системы, я хочу чтобы все адаптеры использовали единый подход к работе с инструментом записи файлов, чтобы обеспечить консистентность и упростить поддержку.

#### Acceptance Criteria

1. WHEN создается новый адаптер, THE Base_Adapter SHALL предоставлять общую логику для работы с инструментом write_file
2. WHEN адаптер поддерживает инструменты, THE Base_Adapter SHALL предоставлять метод для извлечения пути к выходному файлу из промпта
3. WHEN адаптер поддерживает инструменты, THE Base_Adapter SHALL предоставлять метод для чтения результата из файла с fallback на stdout
4. WHEN адаптер не поддерживает инструменты, THE Base_Adapter SHALL использовать только stdout для получения результата

### Requirement 4: Конфигурация разрешенных инструментов

**User Story:** Как администратор системы, я хочу контролировать какие инструменты разрешены для использования моделью, чтобы обеспечить безопасность и ограничить возможности модели.

#### Acceptance Criteria

1. WHEN в конфигурации роли указаны permissions с edit: "*.md", THE Adapter SHALL разрешить только инструмент write_file
2. WHEN в конфигурации роли указаны permissions с edit: "*.md", THE Adapter SHALL ограничить запись только файлами с расширением .md
3. WHEN в конфигурации роли не указаны permissions для edit, THE Adapter SHALL не разрешать использование инструмента write_file
4. WHEN модель пытается использовать неразрешенный инструмент, THE Adapter SHALL отклонить запрос

### Requirement 5: Обработка ошибок при работе с файлами

**User Story:** Как пользователь системы, я хочу получать понятные сообщения об ошибках при проблемах с записью файлов, чтобы быстро диагностировать и исправить проблемы.

#### Acceptance Criteria

1. IF файл не может быть прочитан после выполнения, THEN THE Adapter SHALL логировать предупреждение и использовать stdout
2. IF путь к файлу некорректен, THEN THE Adapter SHALL логировать ошибку и использовать stdout
3. IF файл пустой после записи, THEN THE Adapter SHALL логировать предупреждение и использовать stdout
4. WHEN происходит ошибка чтения файла, THE Adapter SHALL включить информацию об ошибке в metadata ответа

### Requirement 6: Обратная совместимость

**User Story:** Как пользователь существующих workflow, я хочу чтобы изменения не нарушили работу существующих конфигураций, чтобы не пришлось переписывать все workflow.

#### Acceptance Criteria

1. WHEN workflow не указывает outputs в конфигурации шага, THE Adapter SHALL работать как раньше через stdout
2. WHEN в конфигурации роли не указаны permissions, THE Adapter SHALL работать как раньше через stdout
3. WHEN адаптер не поддерживает инструменты, THE Adapter SHALL работать как раньше через stdout
4. WHEN используется старая версия CLI-утилиты без поддержки инструментов, THE Adapter SHALL корректно обрабатывать ошибки и использовать stdout

### Requirement 7: Graceful degradation при отсутствии поддержки инструментов

**User Story:** Как пользователь системы, я хочу чтобы workflow работал даже если модель не поддерживает инструмент write_file, чтобы обеспечить совместимость с разными моделями и версиями CLI.

#### Acceptance Criteria

1. WHEN модель не поддерживает инструмент write_file, THE Model SHALL вывести результат в stdout согласно инструкции в промпте
2. WHEN адаптер не получил файл от модели, THE Adapter SHALL прочитать результат из stdout
3. WHEN адаптер читает результат, THE Adapter SHALL вернуть его в AdapterResponse.content
4. WHEN CLI-утилита возвращает ошибку о неподдерживаемом инструменте, THE Adapter SHALL повторить запрос без флагов инструментов
5. WHEN адаптер использует fallback на stdout, THE Adapter SHALL логировать это действие для отладки
