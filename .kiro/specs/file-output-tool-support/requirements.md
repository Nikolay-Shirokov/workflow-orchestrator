# Requirements Document: Поддержка инструмента записи файлов для адаптеров

## Introduction

Система workflow-оркестратора использует CLI-адаптеры для взаимодействия с различными LLM моделями. При генерации больших текстов (например, документов требований) возникает проблема обрезания вывода при чтении из stdout. Для Gemini уже реализовано решение через разрешение инструмента `write_file`, которое позволяет модели записывать результат напрямую в файл. Необходимо реализовать аналогичный подход для Codex и Claude, сделать это общим решением для всех адаптеров, а также обеспечить безопасность через систему разрешений.

## Glossary

- **Adapter**: Компонент системы, обеспечивающий взаимодействие с конкретной LLM через CLI
- **Codex**: CLI-утилита для взаимодействия с моделями OpenAI
- **Gemini**: CLI-утилита для взаимодействия с моделями Google
- **Claude**: CLI-утилита для взаимодействия с моделями Anthropic
- **write_file**: Инструмент записи файлов в Gemini CLI
- **Write**: Инструмент записи файлов в Claude CLI
- **stdout**: Стандартный поток вывода процесса
- **Workflow**: Последовательность шагов для выполнения задачи
- **Artifact**: Выходной файл, создаваемый на шаге workflow
- **Sandbox**: Режим изоляции, ограничивающий действия модели
- **Permissions**: Набор разрешений, определяющий что модель может делать на шаге

## Requirements

### Requirement 1: Поддержка записи файлов в Codex адаптере

**User Story:** Как пользователь системы, я хочу чтобы Codex адаптер поддерживал запись результатов в файлы, чтобы избежать обрезания больших текстов при чтении из stdout.

#### Acceptance Criteria

1. WHEN в конфигурации шага указан outputs с путем к файлу, THE Codex_Adapter SHALL добавить флаг `--output-last-message <путь>` для сохранения результата
2. WHEN в конфигурации шага permissions.write НЕ указан, THE Codex_Adapter SHALL использовать флаг `--sandbox read-only`
3. WHEN в конфигурации шага permissions.write указан, THE Codex_Adapter SHALL использовать флаг `--sandbox workspace-write`
4. WHEN CLI завершает выполнение, THE Codex_Adapter SHALL прочитать содержимое файла из `--output-last-message` и вернуть его как результат
5. IF файл не был создан, THEN THE Codex_Adapter SHALL использовать stdout как источник результата
6. THE Codex_Adapter SHALL НЕ использовать флаг `--yolo` по умолчанию для обеспечения безопасности

### Requirement 2: Поддержка записи файлов в Claude адаптере

**User Story:** Как пользователь системы, я хочу чтобы Claude адаптер поддерживал запись результатов в файлы через инструмент Write.

#### Acceptance Criteria

1. WHEN в конфигурации шага указан outputs с путем к файлу, THE Claude_Adapter SHALL добавить флаг `--tools` с необходимыми инструментами
2. WHEN в конфигурации шага permissions.write указан, THE Claude_Adapter SHALL включить инструмент `Write` в список `--tools`
3. WHEN инструмент Write разрешен, THE Claude_Adapter SHALL добавить его в `--allowedTools` для выполнения без подтверждения
4. WHEN в конфигурации шага permissions.execute НЕ указан или false, THE Claude_Adapter SHALL НЕ включать инструмент `Bash` в список
5. WHEN модель записывает результат в файл через Write, THE Claude_Adapter SHALL прочитать содержимое файла и вернуть его как результат
6. IF файл не был создан моделью, THEN THE Claude_Adapter SHALL использовать stdout как источник результата
7. THE Claude_Adapter SHALL НЕ использовать флаг `--dangerously-skip-permissions` по умолчанию

### Requirement 3: Автоматическое добавление инструкции записи в файл

**User Story:** Как разработчик workflow, я хочу чтобы система автоматически добавляла инструкцию записи в файл в промпт, чтобы не дублировать эту информацию в каждом шаге.

#### Acceptance Criteria

1. WHEN в конфигурации шага указан outputs с путем к файлу, THE Adapter SHALL автоматически добавить инструкцию записи в конец промпта
2. WHEN добавляется инструкция записи, THE Adapter SHALL использовать имя инструмента специфичное для CLI (`write_file` для Gemini, `Write` для Claude)
3. WHEN добавляется инструкция записи, THE Adapter SHALL включить fallback-инструкцию для вывода в stdout
4. WHEN путь к файлу относительный, THE Adapter SHALL указать что путь относительный к текущей рабочей директории
5. WHEN инструкция добавлена, THE Adapter SHALL сохранить путь к файлу для последующего чтения результата
6. IF в конфигурации шага не указан outputs, THEN THE Adapter SHALL не добавлять инструкцию записи в файл

### Requirement 4: Система разрешений для шагов

**User Story:** Как администратор системы, я хочу контролировать какие действия разрешены модели на каждом шаге, чтобы предотвратить нежелательные изменения в проекте.

#### Acceptance Criteria

1. WHEN в конфигурации шага указан permissions.read, THE Adapter SHALL ограничить чтение только указанными паттернами файлов
2. WHEN в конфигурации шага указан permissions.write, THE Adapter SHALL ограничить запись только указанными паттернами файлов
3. WHEN в конфигурации шага permissions.execute равен false или не указан, THE Adapter SHALL запретить выполнение shell-команд
4. WHEN permissions НЕ указан в шаге, THE Adapter SHALL использовать режим только чтения (read-only)
5. THE Adapter SHALL маппить permissions на соответствующие флаги CLI для каждого адаптера
6. WHEN модель пытается выполнить действие за пределами разрешений, THE CLI SHALL отклонить это действие

### Requirement 5: Унификация подхода для всех адаптеров

**User Story:** Как разработчик системы, я хочу чтобы все адаптеры использовали единый подход к работе с файловым выводом и разрешениями, чтобы обеспечить консистентность и упростить поддержку.

#### Acceptance Criteria

1. WHEN создается новый адаптер, THE Base_Adapter SHALL предоставлять общую логику для формирования инструкции записи
2. WHEN адаптер поддерживает файловый вывод, THE Base_Adapter SHALL предоставлять метод для чтения результата из файла с fallback на stdout
3. WHEN адаптер формирует команду, THE Base_Adapter SHALL предоставлять метод для маппинга permissions на флаги CLI
4. WHEN адаптер не поддерживает файловый вывод, THE Base_Adapter SHALL использовать только stdout для получения результата

### Requirement 6: Обработка ошибок при работе с файлами

**User Story:** Как пользователь системы, я хочу получать понятные сообщения об ошибках при проблемах с записью файлов, чтобы быстро диагностировать и исправить проблемы.

#### Acceptance Criteria

1. IF файл не может быть прочитан после выполнения, THEN THE Adapter SHALL логировать предупреждение и использовать stdout
2. IF путь к файлу некорректен, THEN THE Adapter SHALL логировать ошибку и использовать stdout
3. IF файл пустой после записи, THEN THE Adapter SHALL логировать предупреждение и использовать stdout
4. WHEN происходит ошибка чтения файла, THE Adapter SHALL включить информацию об ошибке в metadata ответа
5. WHEN чтение файла требует ожидания, THE Adapter SHALL использовать polling с таймаутом вместо фиксированной задержки

### Requirement 7: Обратная совместимость

**User Story:** Как пользователь существующих workflow, я хочу чтобы изменения не нарушили работу существующих конфигураций, чтобы не пришлось переписывать все workflow.

#### Acceptance Criteria

1. WHEN workflow не указывает outputs в конфигурации шага, THE Adapter SHALL работать как раньше через stdout
2. WHEN в конфигурации шага не указаны permissions, THE Adapter SHALL использовать безопасный режим read-only
3. WHEN адаптер не поддерживает файловый вывод, THE Adapter SHALL работать как раньше через stdout
4. WHEN используется старая версия CLI-утилиты, THE Adapter SHALL корректно обрабатывать ошибки и использовать stdout

### Requirement 8: Graceful degradation при отсутствии поддержки

**User Story:** Как пользователь системы, я хочу чтобы workflow работал даже если модель не поддерживает инструмент записи файлов, чтобы обеспечить совместимость с разными моделями и версиями CLI.

#### Acceptance Criteria

1. WHEN модель не поддерживает инструмент записи файлов, THE Model SHALL вывести результат в stdout согласно инструкции в промпте
2. WHEN адаптер не получил файл от модели, THE Adapter SHALL прочитать результат из stdout
3. WHEN адаптер читает результат, THE Adapter SHALL вернуть его в AdapterResponse.content
4. WHEN CLI-утилита возвращает ошибку о неподдерживаемом инструменте, THE Adapter SHALL использовать stdout без повторного запроса
5. WHEN адаптер использует fallback на stdout, THE Adapter SHALL логировать это действие для отладки

### Requirement 9: Безопасность и изоляция

**User Story:** Как администратор системы, я хочу предотвратить ситуации когда модель выполняет действия за пределами намерений пользователя.

#### Acceptance Criteria

1. THE Adapter SHALL никогда НЕ использовать режим `--yolo` или `--dangerously-skip-permissions` без явного указания в конфигурации
2. WHEN шаг предназначен для анализа/документации, THE Adapter SHALL использовать режим read-only
3. WHEN шаг предназначен для генерации кода, THE Adapter SHALL ограничить запись только указанными директориями
4. THE System SHALL валидировать permissions перед выполнением шага
5. THE System SHALL логировать все действия модели для аудита
6. WHEN permissions.execute не указан явно, THE Adapter SHALL запретить выполнение shell-команд
