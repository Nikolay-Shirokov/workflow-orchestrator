# Design Document: Комплексное тестирование Workflow Orchestrator

## Обзор

Данный документ описывает дизайн комплексного тестирования Workflow Orchestrator. Тестирование будет проводиться поэтапно, начиная с интеграции реальных адаптеров и заканчивая тестами производительности.

## Компоненты

### 1. Тестовые CLI-адаптеры

**Назначение:** Обертки для реальных CLI-адаптеров с возможностью мокирования

**Интерфейс:**
```typescript
interface TestAdapter {
  name: string;
  command: string;
  available: boolean;
  
  // Проверка доступности
  checkAvailability(): Promise<boolean>;
  
  // Выполнение с таймаутом
  execute(prompt: string, timeout?: number): Promise<string>;
  
  // Мокирование для тестов
  mock(response: string | Error): void;
  unmock(): void;
}
```

### 2. Генератор тестовых workflow

**Назначение:** Создание workflow различной сложности для тестирования

**Возможности:**
- Генерация workflow с заданным количеством шагов
- Создание параллельных и последовательных цепочек
- Добавление условных шагов
- Генерация больших артефактов

**Пример:**
```typescript
const workflow = WorkflowGenerator.create()
  .addSteps(50)
  .withParallelism(5)
  .withConditionals(10)
  .withLargeArtifacts(3, '10MB')
  .build();
```

### 3. Система мониторинга тестов

**Назначение:** Сбор метрик во время выполнения тестов

**Метрики:**
- Время выполнения каждого шага
- Использование памяти
- Количество операций I/O
- Размер артефактов
- Количество попаданий/промахов кэша

### 4. Утилиты для тестирования Resume

**Назначение:** Симуляция прерывания и возобновления процесса

**Функции:**
```typescript
// Прерывание на определенном шаге
interruptAt(stepId: string): void;

// Проверка состояния
validateState(expectedState: WorkflowState): boolean;

// Симуляция повреждения артефакта
corruptArtifact(path: string): void;

// Изменение конфигурации
modifyConfig(changes: Partial<WorkflowConfig>): void;
```

## Стратегия тестирования

### Фаза 1: Интеграция с CLI-адаптерами

**Цель:** Убедиться, что оркестратор корректно работает с реальными AI-моделями

**Подход:**
1. Проверка доступности каждого адаптера
2. Выполнение простого workflow (1-2 шага)
3. Выполнение сложного workflow (5+ шагов с зависимостями)
4. Тестирование обработки ошибок адаптера
5. Тестирование таймаутов

**Тестовые сценарии:**
- ✅ Успешное выполнение с claude-cli
- ✅ Успешное выполнение с openai-cli
- ✅ Успешное выполнение с gemini-cli
- ❌ Адаптер недоступен
- ❌ Адаптер возвращает ошибку
- ⏱️ Адаптер превышает таймаут

### Фаза 2: Обработка ошибок

**Цель:** Проверить устойчивость системы к различным типам ошибок

**Подход:**
1. Создание тестовых workflow с намеренными ошибками
2. Проверка сообщений об ошибках
3. Проверка предложений по устранению
4. Проверка сохранения состояния при ошибке

**Категории ошибок:**
- **Script ошибки**: синтаксис, runtime, exit code
- **Adapter ошибки**: недоступен, таймаут, некорректный ответ
- **Template ошибки**: несуществующие переменные, циклические зависимости
- **Filesystem ошибки**: нет прав, нет места, файл занят
- **Validation ошибки**: невалидная конфигурация, несуществующие зависимости

### Фаза 3: Resume функциональность

**Цель:** Обеспечить надежное возобновление прерванных процессов

**Подход:**
1. Выполнение workflow до определенного шага
2. Симуляция прерывания (Ctrl+C, kill, crash)
3. Восстановление состояния
4. Продолжение выполнения
5. Проверка корректности результата

**Тестовые сценарии:**
- Прерывание на разных этапах (начало, середина, конец)
- Прерывание во время выполнения шага
- Прерывание между шагами
- Повреждение артефактов
- Изменение конфигурации
- Изменение доступности адаптеров

### Фаза 4: Пользовательский ввод

**Цель:** Обеспечить удобный и надежный интерфейс для интерактивного ввода

**Подход:**
1. Создание workflow с user_input шагами
2. Симуляция различных вариантов ввода
3. Проверка валидации
4. Проверка форматирования ответов

**Типы ввода:**
- Текстовый ввод (короткий, длинный, многострочный)
- Выбор из списка (одиночный, множественный)
- Числовой ввод (целые, дробные, диапазоны)
- Булевы значения (yes/no, true/false)
- Отмена ввода (Ctrl+C, ESC)

### Фаза 5: Производительность

**Цель:** Убедиться, что система масштабируется и работает эффективно

**Подход:**
1. Создание больших workflow (50, 100, 200 шагов)
2. Создание больших артефактов (1MB, 10MB, 100MB)
3. Параллельное выполнение (5, 10, 20 шагов)
4. Мониторинг использования ресурсов
5. Профилирование узких мест

**Метрики:**
- Время выполнения workflow
- Использование памяти (heap, RSS)
- Количество операций I/O
- Эффективность кэширования
- Время рендеринга шаблонов

## Correctness Properties

*Свойство корректности - это характеристика или поведение, которое должно выполняться во всех валидных сценариях работы системы.*

### Property 1: Успешная интеграция с адаптерами

*Для любого* доступного CLI-адаптера и валидного промпта, выполнение шага должно завершиться успешно и вернуть непустой ответ.

**Validates: Requirements 1.1, 1.2, 1.3**

### Property 2: Корректная обработка ошибок скриптов

*Для любого* script-шага с ошибкой, система должна вернуть сообщение об ошибке, содержащее тип ошибки и предложения по устранению.

**Validates: Requirements 2.1, 2.2**

### Property 3: Сохранение состояния при ошибке

*Для любого* workflow, если шаг завершается с ошибкой, то состояние должно быть сохранено, и все предыдущие артефакты должны остаться доступными.

**Validates: Requirements 2.2, 3.1**

### Property 4: Resume восстанавливает состояние

*Для любого* прерванного workflow, выполнение resume должно восстановить состояние и продолжить с последнего успешного шага.

**Validates: Requirements 3.2, 3.3**

### Property 5: Артефакты не дублируются при resume

*Для любого* workflow с resume, артефакты успешно выполненных шагов не должны создаваться повторно.

**Validates: Requirements 3.4**

### Property 6: Валидация пользовательского ввода

*Для любого* user_input шага с правилами валидации, невалидный ввод должен быть отклонен с понятным сообщением об ошибке.

**Validates: Requirements 4.2, 4.3**

### Property 7: Производительность больших workflow

*Для любого* workflow с N шагами, время выполнения должно расти линейно O(N), а не экспоненциально.

**Validates: Requirements 5.1**

### Property 8: Эффективность кэширования

*Для любого* артефакта, повторная загрузка из кэша должна быть минимум в 10 раз быстрее, чем загрузка из файла.

**Validates: Requirements 5.4**

### Property 9: Обратная совместимость конфигураций

*Для любой* конфигурации предыдущей версии, новая версия оркестратора должна корректно обработать её без ошибок.

**Validates: Requirements 7.1, 7.2**

## Error Handling

### Категории ошибок

1. **Configuration Errors**: Невалидная конфигурация workflow
2. **Execution Errors**: Ошибки во время выполнения шагов
3. **Adapter Errors**: Проблемы с CLI-адаптерами
4. **Filesystem Errors**: Проблемы с файловой системой
5. **Validation Errors**: Ошибки валидации данных

### Стратегия обработки

- Все ошибки должны содержать понятное сообщение
- Критические ошибки должны сохранять состояние
- Recoverable ошибки должны предлагать retry
- Все ошибки должны логироваться с полным контекстом

## Testing Strategy

### Unit Tests

- Тестирование отдельных компонентов (адаптеры, генераторы, утилиты)
- Тестирование граничных случаев
- Тестирование обработки ошибок

### Integration Tests

- Тестирование взаимодействия компонентов
- Тестирование реальных CLI-адаптеров
- Тестирование полных workflow

### Property-Based Tests

- Минимум 100 итераций на тест
- Генерация случайных workflow
- Генерация случайных входных данных
- Проверка инвариантов системы

### Performance Tests

- Бенчмарки для критических операций
- Профилирование использования памяти
- Тестирование под нагрузкой
