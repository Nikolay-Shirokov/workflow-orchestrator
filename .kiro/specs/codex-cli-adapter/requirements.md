# Требования: Адаптер Codex CLI

## Введение

Данный документ описывает требования к реализации адаптера для интеграции Codex CLI в систему DualDesign. Адаптер должен обеспечить возможность выполнения запросов к моделям OpenAI через утилиту командной строки Codex CLI.

## Глоссарий

- **Codex_CLI**: Утилита командной строки от OpenAI для взаимодействия с моделями GPT через терминал
- **Adapter**: Компонент системы, обеспечивающий интеграцию с внешним CLI-инструментом
- **System**: Система DualDesign для оркестрации рабочих процессов с AI-моделями
- **Exec_Mode**: Неинтерактивный режим выполнения команд Codex CLI
- **Session**: Сессия взаимодействия с моделью, которую можно возобновить

## Требования

### Требование 1: Базовая интеграция с Codex CLI

**User Story:** Как разработчик системы, я хочу интегрировать Codex CLI, чтобы пользователи могли использовать модели OpenAI через эту утилиту.

#### Критерии приемки

1. THE Adapter SHALL наследоваться от BaseCLIAdapter
2. WHEN создается экземпляр адаптера, THE Adapter SHALL использовать команду `codex exec` для неинтерактивного выполнения
3. THE Adapter SHALL поддерживать передачу промпта через аргумент командной строки
4. THE Adapter SHALL поддерживать передачу промпта через stdin с использованием флага `-`
5. THE Adapter SHALL иметь уникальное имя `codex-cli` и версию `1.0.0`

### Требование 2: Конфигурация модели

**User Story:** Как пользователь, я хочу указывать конкретную модель для использования, чтобы контролировать, какая версия GPT обрабатывает мои запросы.

#### Критерии приемки

1. WHEN в запросе указана модель, THE Adapter SHALL добавлять флаг `--model` или `-m` с именем модели
2. WHEN модель не указана, THE Adapter SHALL использовать модель по умолчанию из конфигурации Codex CLI
3. THE Adapter SHALL поддерживать все модели, доступные через Codex CLI (например, `gpt-4`, `gpt-3.5-turbo`)

### Требование 3: Управление режимами выполнения

**User Story:** Как администратор системы, я хочу контролировать режим выполнения команд, чтобы обеспечить безопасность и автоматизацию.

#### Критерии приемки

1. THE Adapter SHALL поддерживать флаг `--full-auto` для автоматического выполнения без запросов подтверждения
2. THE Adapter SHALL поддерживать флаг `--sandbox` для управления политикой песочницы
3. WHEN требуется полная автоматизация, THE Adapter SHALL использовать флаг `--full-auto`
4. THE Adapter SHALL поддерживать флаг `--cd` для установки рабочей директории

### Требование 4: Обработка вывода

**User Story:** Как разработчик, я хочу получать структурированный вывод от Codex CLI, чтобы легко обрабатывать ответы модели.

#### Критерии приемки

1. THE Adapter SHALL поддерживать флаг `--json` для получения вывода в формате JSONL
2. WHEN используется JSON-режим, THE Adapter SHALL парсить newline-delimited JSON события
3. WHEN используется текстовый режим, THE Adapter SHALL извлекать финальное сообщение ассистента из вывода
4. THE Adapter SHALL корректно обрабатывать многострочный вывод
5. THE Adapter SHALL удалять служебную информацию и метаданные из ответа

### Требование 5: Управление сессиями

**User Story:** Как пользователь, я хочу возобновлять предыдущие сессии, чтобы продолжить диалог с моделью.

#### Критерии приемки

1. THE Adapter SHALL поддерживать команду `codex exec resume` для возобновления сессий
2. WHEN указан ID сессии, THE Adapter SHALL возобновлять указанную сессию
3. WHEN используется флаг `--last`, THE Adapter SHALL возобновлять последнюю сессию
4. THE Adapter SHALL поддерживать передачу дополнительного промпта при возобновлении сессии

### Требование 6: Обработка ошибок

**User Story:** Как пользователь, я хочу получать понятные сообщения об ошибках, чтобы быстро диагностировать проблемы.

#### Критерии приемки

1. WHEN Codex CLI недоступен, THE Adapter SHALL возвращать ошибку `ADAPTER_NOT_FOUND`
2. WHEN возникает ошибка аутентификации, THE Adapter SHALL возвращать ошибку `ADAPTER_AUTH_ERROR`
3. WHEN команда превышает таймаут, THE Adapter SHALL возвращать ошибку `ADAPTER_TIMEOUT`
4. WHEN возникает ошибка выполнения, THE Adapter SHALL включать stderr в сообщение об ошибке
5. THE Adapter SHALL корректно определять, можно ли повторить операцию после ошибки

### Требование 7: Проверка доступности

**User Story:** Как система, я хочу проверять доступность Codex CLI перед использованием, чтобы избежать ошибок выполнения.

#### Критерии приемки

1. THE Adapter SHALL реализовывать метод `isAvailable()`
2. WHEN вызывается `isAvailable()`, THE Adapter SHALL выполнять команду `codex --version`
3. WHEN команда выполняется успешно, THE Adapter SHALL возвращать `true`
4. WHEN команда не выполняется, THE Adapter SHALL возвращать `false`
5. THE Adapter SHALL использовать таймаут 5 секунд для проверки доступности

### Требование 8: Поддержка дополнительных опций

**User Story:** Как продвинутый пользователь, я хочу использовать дополнительные опции Codex CLI, чтобы настроить поведение под свои нужды.

#### Критерии приемки

1. THE Adapter SHALL поддерживать флаг `--search` для включения веб-поиска
2. THE Adapter SHALL поддерживать флаг `--output-last-message` для сохранения финального сообщения
3. THE Adapter SHALL поддерживать флаг `--color` для управления ANSI-цветами в выводе
4. THE Adapter SHALL поддерживать флаг `--config` для переопределения конфигурационных значений
5. THE Adapter SHALL поддерживать флаг `--profile` для выбора профиля конфигурации

### Требование 9: Регистрация адаптера

**User Story:** Как система, я хочу автоматически регистрировать Codex CLI адаптер, чтобы он был доступен для использования.

#### Критерии приемки

1. THE Adapter SHALL быть экспортирован из модуля `src/adapters/index.ts`
2. THE Adapter SHALL быть зарегистрирован в AdapterRegistry
3. WHEN система запускается, THE Adapter SHALL быть доступен по имени `codex-cli`
4. THE Adapter SHALL быть включен в список доступных адаптеров

### Требование 10: Тестирование

**User Story:** Как разработчик, я хочу иметь тесты для адаптера, чтобы гарантировать его корректную работу.

#### Критерии приемки

1. THE System SHALL включать unit-тесты для базовой функциональности адаптера
2. THE System SHALL включать тесты для парсинга JSON-вывода
3. THE System SHALL включать тесты для парсинга текстового вывода
4. THE System SHALL включать тесты для обработки ошибок
5. THE System SHALL включать тесты для проверки доступности
