# Дизайн: Интерактивный интерфейс CLI

## Обзор

Данный документ описывает дизайн интерактивного интерфейса для консольной утилиты Workflow Orchestrator. Интерфейс предоставляет структурированное отображение прогресса выполнения процесса с возможностью переключения между интерактивным и логовым режимами.

### Цели дизайна

1. Улучшить пользовательский опыт за счет структурированного отображения
2. Обеспечить обратную совместимость с текущим логовым режимом
3. Предоставить интерактивные возможности для управления процессом
4. Минимизировать зависимости и использовать легковесные решения

### Взаимодействие компонентов

1. **CLI Layer** - точка входа, обработка аргументов командной строки
2. **Display Layer** - выбор режима отображения (интерактивный/логовый)
3. **Terminal Layer** - низкоуровневая работа с терминалом



## Компоненты и интерфейсы

### 1. TerminalRenderer

Низкоуровневый компонент для работы с терминалом.

```typescript
interface TerminalRenderer {
  // Управление курсором
  moveCursor(x: number, y: number): void;
  clearScreen(): void;
  clearLine(): void;
  hideCursor(): void;
  showCursor(): void;
  
  // Цветовое форматирование
  colorize(text: string, color: TerminalColor): string;
  bold(text: string): string;
  dim(text: string): string;
  
  // Информация о терминале
  getSize(): { width: number; height: number };
  onResize(callback: () => void): void;
  
  // Вывод текста
  write(text: string): void;
  writeLine(text: string): void;
}

enum TerminalColor {
  Reset = '\x1b[0m',
  Red = '\x1b[31m',
  Green = '\x1b[32m',
  Yellow = '\x1b[33m',
  Blue = '\x1b[34m',
  Magenta = '\x1b[35m',
  Cyan = '\x1b[36m',
  Gray = '\x1b[90m',
  White = '\x1b[37m'
}
```

**Реализация**: Использует ANSI escape codes для управления терминалом. Не требует внешних зависимостей.

## Correctness Properties

*Свойство (property) - это характеристика или поведение, которое должно выполняться для всех допустимых выполнений системы - по сути, формальное утверждение о том, что система должна делать. Свойства служат мостом между человекочитаемыми спецификациями и машинно-проверяемыми гарантиями корректности.*

### Property 1: Выбор режима отображения на основе флага

*Для любой* конфигурации запуска, если указан флаг `--log-mode`, то система должна использовать логовый режим, иначе - интерактивный режим.

**Validates: Requirements 1.2, 1.3**

### Property 2: Неизменность режима отображения

*Для любой* сессии выполнения, режим отображения, выбранный при инициализации, должен оставаться неизменным на протяжении всей сессии.

**Validates: Requirements 1.4**

### Property 3: Наличие обязательных секций в интерактивном режиме

*Для любого* вывода в интерактивном режиме, должны присутствовать все обязательные секции: заголовок, путь к артефактам, список шагов, текущий шаг, история, прогресс.

**Validates: Requirements 2.1**

### Property 4: Цветовая индикация статусов

*Для любого* вывода в интерактивном режиме, статусы шагов должны содержать соответствующие ANSI escape codes: зеленый для завершенных, желтый для текущего, серый для ожидающих, красный для ошибок.

**Validates: Requirements 2.3**

### Property 5: Формат отображения списка шагов

*Для любого* списка шагов, каждый шаг должен отображаться в формате: номер, иконка статуса, название, ID.

**Validates: Requirements 3.1**



### Property 6: Обновление статуса шага

*Для любого* шага, когда он завершается, его статус в списке должен измениться с "выполняется" на "завершен" или "ошибка".

**Validates: Requirements 3.3**

### Property 7: Полнота информации о текущем шаге

*Для любого* текущего выполняемого шага, отображение должно содержать: название, ID, тип, роль (если применимо), адаптер (если применимо), модель (если применимо), время выполнения.

**Validates: Requirements 4.1, 4.2, 4.3**

### Property 8: Ограничение размера истории

*Для любой* истории последних действий, количество отображаемых элементов не должно превышать 3.

**Validates: Requirements 5.1, 5.2**

### Property 9: Корректность вычисления прогресса

*Для любого* состояния выполнения, процент прогресса должен равняться (завершенные шаги / общее количество шагов) * 100.

**Validates: Requirements 6.2**

### Property 10: Формат прогресс-бара

*Для любого* прогресс-бара, его длина должна быть фиксированной, а количество заполненных символов должно соответствовать проценту выполнения.

**Validates: Requirements 6.1**

### Property 11: Обратная совместимость логового режима

*Для любого* процесса, запущенного в логовом режиме, вывод должен быть идентичен текущей реализации ProgressDisplay.

**Validates: Requirements 7.1, 7.2, 7.3**

### Property 12: Отображение параллельных шагов

*Для любого* набора параллельно выполняемых шагов, все шаги должны отображаться в секции текущих шагов с индикатором параллельного выполнения.

**Validates: Requirements 9.1, 9.2, 9.3**



### Property 13: Навигация в интерактивном меню

*Для любого* интерактивного меню, нажатие стрелок вверх/вниз должно изменять выбранную опцию, а нажатие Enter должно возвращать значение выбранной опции.

**Validates: Requirements 10.1.2, 10.1.3**

### Property 14: Полнота итоговой информации

*Для любого* завершенного процесса, итоговая информация должна содержать: статус, время выполнения, количество завершенных шагов, количество артефактов, ID сессии.

**Validates: Requirements 11.1, 11.2, 11.3**

### Property 15: Определение основного выходного документа

*Для любого* набора артефактов, основной выходной документ должен быть последним созданным файлом с расширением .md, .txt, .yaml или .json.

**Validates: Requirements 12.2**

### Property 16: Позиционирование при возобновлении

*Для любого* процесса возобновления, курсор должен автоматически позиционироваться на первом незавершенном шаге.

**Validates: Requirements 13.3**

### Property 17: Инициализация артефактов при возобновлении

*Для любого* выбранного шага при возобновлении, процесс должен быть инициализирован артефактами всех предыдущих шагов, а артефакты выбранного и последующих шагов должны быть проигнорированы.

**Validates: Requirements 13.5, 13.6**



## Обработка ошибок

### 1. Ошибки терминала

**Проблема**: Терминал не поддерживает ANSI escape codes или слишком узкий.

**Решение**:
- Определять поддержку ANSI codes через переменные окружения (`TERM`, `COLORTERM`)
- При отсутствии поддержки автоматически переключаться в логовый режим
- При ширине терминала < 60 символов отображать предупреждение и использовать упрощенный формат

### 2. Ошибки ввода пользователя

**Проблема**: Пользователь вводит некорректные данные в интерактивном меню.

**Решение**:
- Валидировать ввод и отображать сообщение об ошибке
- Не позволять выбрать недопустимую опцию
- Предоставлять подсказки о допустимых действиях

### 3. Ошибки изменения размера терминала

**Проблема**: Размер терминала изменяется во время выполнения.

**Решение**:
- Подписаться на событие `process.stdout.on('resize')`
- Перерисовывать интерфейс с учетом новых размеров
- Адаптировать ширину прогресс-бара и длину строк

### 4. Ошибки открытия редактора

**Проблема**: Не удается открыть редактор для просмотра результатов.

**Решение**:
- Отображать сообщение об ошибке
- Предлагать альтернативные способы просмотра (вывод пути к файлу)
- Логировать ошибку для отладки



## Стратегия тестирования

### Двойной подход к тестированию

Система будет тестироваться с использованием двух дополняющих друг друга подходов:

1. **Unit тесты** - проверка конкретных примеров, граничных случаев и условий ошибок
2. **Property-based тесты** - проверка универсальных свойств на множестве сгенерированных входных данных

### Unit тесты

**Фокус**: Конкретные примеры и граничные случаи

- Тестирование форматирования вывода с известными данными
- Проверка обработки специальных символов в названиях шагов
- Тестирование граничных случаев (0 шагов, 1 шаг, много шагов)
- Проверка обработки ошибок (недоступный терминал, некорректный ввод)
- Интеграционные тесты с реальными компонентами

**Примеры тестов**:
- `should format step list correctly with 3 steps`
- `should handle empty step list`
- `should escape special characters in step names`
- `should fall back to log mode when terminal is too narrow`

### Property-based тесты

**Фокус**: Универсальные свойства на случайных данных

**Библиотека**: `fast-check` (уже в зависимостях проекта)

**Конфигурация**: Минимум 100 итераций на тест

**Формат тегов**: `Feature: interactive-cli-interface, Property {number}: {property_text}`

**Примеры свойств для тестирования**:

1. **Property 1**: Выбор режима на основе флага
   - Генератор: случайные конфигурации с/без флага `--log-mode`
   - Проверка: режим соответствует наличию флага

2. **Property 2**: Неизменность режима
   - Генератор: случайные последовательности событий
   - Проверка: режим не меняется после инициализации

3. **Property 9**: Корректность вычисления прогресса
   - Генератор: случайные состояния выполнения (0-100 шагов, 0-N завершено)
   - Проверка: процент = (завершено / всего) * 100

4. **Property 15**: Определение основного документа
   - Генератор: случайные списки артефактов с разными расширениями
   - Проверка: выбирается последний файл с правильным расширением

### Генераторы для Property-based тестов

```typescript
// Генератор конфигураций запуска
const configArbitrary = fc.record({
  logMode: fc.boolean(),
  workflowName: fc.string({ minLength: 1, maxLength: 50 }),
  steps: fc.array(stepArbitrary, { minLength: 0, maxLength: 20 })
});

// Генератор информации о шаге
const stepArbitrary = fc.record({
  id: fc.string({ minLength: 1, maxLength: 20 }),
  name: fc.string({ minLength: 1, maxLength: 100 }),
  status: fc.constantFrom('pending', 'running', 'completed', 'failed'),
  duration: fc.option(fc.nat({ max: 60000 }))
});

// Генератор списка артефактов
const artifactsArbitrary = fc.array(
  fc.record({
    path: fc.string({ minLength: 1, maxLength: 100 }),
    extension: fc.constantFrom('.md', '.txt', '.yaml', '.json', '.log', '.tmp')
  }),
  { minLength: 0, maxLength: 50 }
);
```

### Интеграционное тестирование

**Подход**: Тестирование с mock терминалом

- Создание mock объекта для `process.stdout`
- Перехват вывода и проверка содержимого
- Симуляция ввода пользователя через `process.stdin`
- Проверка последовательности вызовов

**Примеры интеграционных тестов**:
- Полный цикл выполнения процесса в интерактивном режиме
- Возобновление процесса с выбором шага
- Обработка параллельного выполнения
- Открытие результатов после завершения
