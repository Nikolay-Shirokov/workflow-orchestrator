# Requirements Document

## Introduction

Данный документ описывает требования к инструменту оркестрации рабочих процессов (Workflow Orchestrator) - настраиваемой системе для автоматизации многошаговых процессов с использованием различных AI-моделей через консольные утилиты. Инструмент предназначен для замены AI-оркестратора на скриптовый, обеспечивая стабильное и предсказуемое выполнение рабочих процессов даже с менее продвинутыми моделями.

## Glossary

- **Workflow Orchestrator** (Оркестратор) - система управления рабочими процессами
- **Workflow** (Рабочий процесс) - последовательность шагов для достижения цели
- **Step** (Шаг) - единица работы в рабочем процессе
- **State** (Состояние) - текущее положение выполнения процесса
- **Artifact** (Артефакт) - файл с результатом выполнения шага
- **CLI Adapter** (CLI-адаптер) - обертка для взаимодействия с консольной утилитой AI-модели
- **Prompt Template** (Шаблон промпта) - текстовый шаблон с переменными для формирования запроса к модели
- **Session** (Сессия) - экземпляр выполнения рабочего процесса
- **DSL** (Domain Specific Language) - специализированный язык для описания рабочих процессов
- **Resume** (Возобновление) - продолжение выполнения процесса с сохраненного состояния

## Requirements

### Requirement 1

**User Story:** Как пользователь, я хочу определять консольные команды для взаимодействия с различными AI-моделями, чтобы использовать доступные мне инструменты и лимиты подписок.

#### Acceptance Criteria

1. WHEN пользователь создает конфигурацию CLI-адаптера THEN система SHALL сохранить параметры команды, аргументов и переменных окружения
2. WHEN система вызывает CLI-адаптер THEN система SHALL выполнить консольную команду с подстановкой параметров
3. WHEN CLI-команда завершается THEN система SHALL захватить stdout и stderr для дальнейшей обработки
4. WHERE пользователь определяет несколько адаптеров THEN система SHALL поддерживать множественные конфигурации для разных моделей
5. WHEN CLI-команда возвращает ошибку THEN система SHALL логировать ошибку и предоставить возможность повтора или пропуска шага

### Requirement 2

**User Story:** Как пользователь, я хочу описывать рабочие процессы декларативно, чтобы легко создавать, изменять и переиспользовать процессы.

#### Acceptance Criteria

1. WHEN пользователь создает описание процесса THEN система SHALL поддерживать YAML или JSON формат конфигурации
2. WHEN описание процесса содержит последовательность шагов THEN система SHALL валидировать структуру и зависимости между шагами
3. WHERE процесс содержит условные переходы THEN система SHALL поддерживать условную логику выполнения шагов
4. WHEN пользователь определяет шаг процесса THEN система SHALL позволить указать CLI-адаптер, шаблон промпта, входные и выходные артефакты
5. WHEN описание процесса содержит циклы или повторения THEN система SHALL поддерживать итеративные конструкции

### Requirement 3

**User Story:** Как пользователь, я хочу использовать шаблоны промптов с переменными, чтобы динамически формировать запросы к моделям на основе результатов предыдущих шагов.

#### Acceptance Criteria

1. WHEN пользователь создает шаблон промпта THEN система SHALL поддерживать синтаксис подстановки переменных (например, `{variable_name}`)
2. WHEN система выполняет шаг THEN система SHALL подставить значения переменных из контекста выполнения
3. WHERE переменная ссылается на артефакт предыдущего шага THEN система SHALL загрузить содержимое файла и подставить в шаблон
4. WHEN шаблон содержит условные блоки THEN система SHALL поддерживать условное включение текста
5. WHEN переменная не определена THEN система SHALL выдать ошибку с указанием отсутствующей переменной

### Requirement 4

**User Story:** Как пользователь, я хочу отслеживать состояние выполнения процесса, чтобы понимать текущий прогресс и иметь возможность возобновления.

#### Acceptance Criteria

1. WHEN процесс начинает выполнение THEN система SHALL создать файл состояния с метаданными сессии
2. WHEN шаг завершается успешно THEN система SHALL обновить состояние с отметкой о завершении шага
3. WHEN процесс прерывается THEN система SHALL сохранить текущее состояние для возможности возобновления
4. WHERE пользователь запрашивает статус THEN система SHALL отобразить текущий шаг, завершенные шаги и оставшиеся шаги
5. WHEN система сохраняет состояние THEN система SHALL включить timestamp, идентификатор сессии, текущий шаг и пути к артефактам

### Requirement 5

**User Story:** Как пользователь, я хочу останавливать и возобновлять выполнение процесса, чтобы контролировать ход выполнения и экономить ресурсы.

#### Acceptance Criteria

1. WHEN пользователь отправляет команду остановки THEN система SHALL корректно завершить текущий шаг и сохранить состояние
2. WHEN пользователь запускает возобновление процесса THEN система SHALL загрузить сохраненное состояние и продолжить с последнего завершенного шага
3. WHERE состояние указывает на незавершенный шаг THEN система SHALL предложить повторить или пропустить этот шаг
4. WHEN пользователь возобновляет процесс THEN система SHALL валидировать целостность артефактов предыдущих шагов
5. IF артефакты повреждены или отсутствуют THEN система SHALL сообщить об ошибке и предложить начать с более раннего шага

### Requirement 6

**User Story:** Как пользователь, я хочу вручную изменять состояние процесса, чтобы начать выполнение с произвольного шага или исправить ошибки.

#### Acceptance Criteria

1. WHEN пользователь редактирует файл состояния THEN система SHALL валидировать изменения перед возобновлением
2. WHEN пользователь указывает начальный шаг THEN система SHALL начать выполнение с указанного шага
3. WHERE пользователь изменяет артефакты THEN система SHALL использовать измененные артефакты при выполнении
4. WHEN пользователь откатывает состояние на предыдущий шаг THEN система SHALL позволить повторное выполнение с этого шага
5. IF состояние содержит некорректные данные THEN система SHALL выдать детальное сообщение об ошибке валидации

### Requirement 7

**User Story:** Как пользователь, я хочу сохранять все промежуточные результаты в файлы, чтобы иметь полную прозрачность процесса и возможность анализа.

#### Acceptance Criteria

1. WHEN шаг завершается THEN система SHALL сохранить результат в файл артефакта с именем согласно конфигурации
2. WHEN система создает артефакты THEN система SHALL организовать их в структуру директорий по сессиям
3. WHERE шаг производит множественные выходы THEN система SHALL поддерживать сохранение нескольких артефактов на шаг
4. WHEN артефакт сохраняется THEN система SHALL добавить метаданные (timestamp, имя шага, версия)
5. WHEN пользователь запрашивает артефакты THEN система SHALL предоставить список всех артефактов сессии с их статусами

### Requirement 8

**User Story:** Как пользователь, я хочу реализовать рабочий процесс из существующего dual-design режима, чтобы сохранить функциональность с улучшенной стабильностью.

#### Acceptance Criteria

1. WHEN пользователь запускает dual-design процесс THEN система SHALL выполнить 9 шагов согласно спецификации
2. WHEN система выполняет шаг с двумя моделями THEN система SHALL поддерживать параллельное или последовательное выполнение
3. WHERE шаг требует веб-исследования THEN система SHALL поддерживать условное выполнение опционального шага 1.5
4. WHEN процесс достигает шага 8 THEN система SHALL приостановить выполнение для получения ответов пользователя
5. WHEN пользователь предоставляет ответы THEN система SHALL продолжить выполнение с генерацией финального документа

### Requirement 9

**User Story:** Как пользователь, я хочу использовать различные консольные утилиты для AI-моделей, чтобы оптимизировать соотношение качества и цены.

#### Acceptance Criteria

1. WHEN пользователь настраивает адаптер THEN система SHALL поддерживать claude-cli, codex-cli, gemini-cli и другие утилиты
2. WHERE адаптер требует аутентификации THEN система SHALL поддерживать передачу API ключей через переменные окружения
3. WHEN система вызывает разные утилиты THEN система SHALL нормализовать выходные данные к единому формату
4. WHERE утилита имеет специфичный формат вывода THEN система SHALL поддерживать настраиваемые парсеры ответов
5. WHEN утилита недоступна THEN система SHALL выдать понятное сообщение об ошибке с предложением альтернатив

### Requirement 10

**User Story:** Как пользователь, я хочу определять произвольные рабочие процессы, чтобы автоматизировать различные задачи помимо dual-design.

#### Acceptance Criteria

1. WHEN пользователь создает новый процесс THEN система SHALL позволить определить произвольную последовательность шагов
2. WHERE процесс использует переиспользуемые компоненты THEN система SHALL поддерживать библиотеку шаблонов шагов
3. WHEN пользователь определяет процесс THEN система SHALL валидировать корректность ссылок на артефакты и переменные
4. WHERE процесс содержит вложенные подпроцессы THEN система SHALL поддерживать композицию процессов
5. WHEN пользователь сохраняет процесс THEN система SHALL позволить переиспользовать его как шаблон

### Requirement 11

**User Story:** Как пользователь, я хочу иметь простой DSL для описания процессов, чтобы быстро создавать процессы без глубокого знания YAML/JSON.

#### Acceptance Criteria

1. WHEN пользователь пишет DSL-описание THEN система SHALL транслировать его в внутреннее представление процесса
2. WHEN DSL содержит синтаксические ошибки THEN система SHALL выдать понятное сообщение с указанием строки и характера ошибки
3. WHERE DSL поддерживает сокращенный синтаксис THEN система SHALL разворачивать сокращения в полную конфигурацию
4. WHEN пользователь использует DSL THEN система SHALL поддерживать основные конструкции: step, prompt, artifact, condition, loop
5. WHEN DSL-файл обрабатывается THEN система SHALL генерировать эквивалентную YAML/JSON конфигурацию для отладки

### Requirement 12

**User Story:** Как пользователь, я хочу видеть логи выполнения процесса, чтобы отслеживать прогресс и диагностировать проблемы.

#### Acceptance Criteria

1. WHEN процесс выполняется THEN система SHALL выводить логи в консоль с указанием текущего шага
2. WHEN шаг начинается THEN система SHALL логировать имя шага, используемый адаптер и входные параметры
3. WHEN шаг завершается THEN система SHALL логировать статус завершения, время выполнения и путь к артефакту
4. WHERE происходит ошибка THEN система SHALL логировать детальную информацию об ошибке с контекстом
5. WHEN пользователь запрашивает детальные логи THEN система SHALL поддерживать уровни логирования (debug, info, warning, error)

### Requirement 13

**User Story:** Как пользователь, я хочу иметь возможность dry-run выполнения процесса, чтобы проверить корректность конфигурации без реальных вызовов моделей.

#### Acceptance Criteria

1. WHEN пользователь запускает dry-run THEN система SHALL валидировать конфигурацию процесса без выполнения CLI-команд
2. WHEN dry-run выполняется THEN система SHALL отобразить последовательность шагов с подставленными параметрами
3. WHERE dry-run обнаруживает ошибки THEN система SHALL вывести все найденные проблемы с указанием их местоположения
4. WHEN dry-run завершается успешно THEN система SHALL подтвердить готовность процесса к реальному выполнению
5. WHEN пользователь использует dry-run THEN система SHALL проверить доступность всех необходимых файлов и переменных

### Requirement 14

**User Story:** Как разработчик, я хочу расширять систему новыми типами адаптеров, чтобы интегрировать дополнительные инструменты.

#### Acceptance Criteria

1. WHEN разработчик создает новый адаптер THEN система SHALL предоставить интерфейс для реализации
2. WHERE адаптер требует специфичной обработки THEN система SHALL поддерживать переопределение методов парсинга и форматирования
3. WHEN новый адаптер регистрируется THEN система SHALL автоматически делать его доступным в конфигурациях процессов
4. WHERE адаптер использует нестандартный протокол THEN система SHALL позволить определить кастомную логику взаимодействия
5. WHEN адаптер загружается THEN система SHALL валидировать его совместимость с текущей версией оркестратора

### Requirement 15

**User Story:** Как пользователь, я хочу получать структурированные запросы на ввод данных, чтобы удобно предоставлять информацию в процессе выполнения.

#### Acceptance Criteria

1. WHEN шаг требует ввода пользователя THEN система SHALL поддерживать определение формата ожидаемого ответа в промпте
2. WHEN модель возвращает структурированный список вопросов THEN система SHALL парсить ответ согласно указанному формату (JSON, YAML, Markdown)
3. WHERE ответ содержит список вопросов THEN система SHALL представить их пользователю в интерактивной форме
4. WHEN пользователь отвечает на вопросы THEN система SHALL валидировать ответы согласно определенным правилам (обязательность, тип данных)
5. WHEN все ответы собраны THEN система SHALL форматировать их согласно шаблону и передать в следующий шаг процесса

### Requirement 16

**User Story:** Как пользователь, я хочу использовать разные модели для разных ролей в процессе, чтобы получить преимущества от различных перспектив и специализаций моделей.

#### Acceptance Criteria

1. WHEN пользователь определяет шаг процесса THEN система SHALL позволить указать конкретную модель или CLI-адаптер для этого шага
2. WHERE процесс использует несколько ролей THEN система SHALL поддерживать назначение разных моделей на разные роли
3. WHEN система выполняет шаг THEN система SHALL использовать модель, указанную для этого шага или роли
4. WHERE модель не указана явно THEN система SHALL использовать модель по умолчанию из конфигурации
5. WHEN пользователь настраивает роли THEN система SHALL позволить определить специализированные промпты для каждой роли

### Requirement 17

**User Story:** Как пользователь, я хочу использовать специализированные режимы работы для разных ролей, чтобы модели вели себя согласно своему назначению в процессе.

#### Acceptance Criteria

1. WHEN пользователь определяет роль THEN система SHALL позволить указать roleDefinition с описанием поведения роли
2. WHERE роль требует специфичного поведения THEN система SHALL поддерживать customInstructions для детальной настройки
3. WHEN система вызывает модель для роли THEN система SHALL включить roleDefinition в контекст запроса
4. WHERE роль имеет ограничения THEN система SHALL поддерживать определение запрещенных действий (например, запрет ask_followup_question)
5. WHEN пользователь создает процесс THEN система SHALL позволить переиспользовать определения ролей из библиотеки

### Requirement 18

**User Story:** Как пользователь, я хочу использовать MCP-инструменты в процессе, чтобы расширить возможности моделей дополнительными функциями (веб-поиск, работа с файлами и т.д.).

#### Acceptance Criteria

1. WHEN система инициализирует процесс THEN система SHALL проверить доступность MCP-инструментов
2. WHERE шаг требует MCP-инструмент THEN система SHALL поддерживать условное выполнение шага в зависимости от доступности инструмента
3. WHEN MCP-инструмент доступен THEN система SHALL передать информацию о доступных инструментах в контекст модели
4. WHERE процесс использует веб-поиск THEN система SHALL поддерживать автоматическое определение необходимости поиска на основе контекста
5. WHEN MCP-инструмент недоступен THEN система SHALL логировать предупреждение и пропустить опциональные шаги, зависящие от него

### Requirement 19

**User Story:** Как пользователь, я хочу использовать группы разрешений для контроля доступа к файлам и командам, чтобы обеспечить безопасность выполнения процессов.

#### Acceptance Criteria

1. WHEN пользователь определяет процесс THEN система SHALL позволить указать группы разрешений (read, edit, command, mcp)
2. WHERE процесс требует редактирования файлов THEN система SHALL поддерживать определение fileRegex для ограничения доступа
3. WHEN система выполняет шаг THEN система SHALL проверять разрешения перед выполнением операций
4. WHERE разрешения недостаточны THEN система SHALL выдать ошибку с указанием требуемых разрешений
5. WHEN пользователь настраивает разрешения THEN система SHALL валидировать корректность регулярных выражений для файлов

### Requirement 20

**User Story:** Как пользователь, я хочу видеть прогресс выполнения процесса в реальном времени, чтобы понимать, что происходит на каждом шаге.

#### Acceptance Criteria

1. WHEN шаг начинается THEN система SHALL отобразить уведомление с именем шага и используемой моделью
2. WHEN шаг завершается THEN система SHALL отобразить статус завершения, время выполнения и путь к артефакту
3. WHERE процесс содержит множество шагов THEN система SHALL отображать индикатор прогресса (текущий шаг / всего шагов)
4. WHEN происходит ошибка THEN система SHALL отобразить детальное сообщение с контекстом и предложением действий
5. WHEN пользователь запрашивает статус THEN система SHALL отобразить визуальное представление выполненных и оставшихся шагов

### Requirement 21

**User Story:** Как пользователь, я хочу выполнять независимые шаги параллельно, чтобы ускорить выполнение процесса.

#### Acceptance Criteria

1. WHEN пользователь определяет шаги без зависимостей THEN система SHALL позволить пометить их для параллельного выполнения
2. WHERE шаги выполняются параллельно THEN система SHALL запускать их одновременно и ждать завершения всех
3. WHEN параллельные шаги завершаются THEN система SHALL собрать все артефакты перед переходом к следующему шагу
4. WHERE один из параллельных шагов завершается с ошибкой THEN система SHALL дождаться завершения остальных и сообщить о всех ошибках
5. WHEN пользователь просматривает логи THEN система SHALL четко отображать параллельное выполнение шагов

### Requirement 22

**User Story:** Как пользователь, я хочу экспортировать и импортировать конфигурации процессов, чтобы делиться ими с командой и переиспользовать в разных проектах.

#### Acceptance Criteria

1. WHEN пользователь экспортирует процесс THEN система SHALL создать самодостаточный файл конфигурации со всеми зависимостями
2. WHERE конфигурация содержит ссылки на внешние файлы THEN система SHALL поддерживать опцию включения содержимого файлов в экспорт
3. WHEN пользователь импортирует процесс THEN система SHALL валидировать совместимость с текущей версией оркестратора
4. WHERE импортируемый процесс конфликтует с существующим THEN система SHALL предложить варианты разрешения конфликта
5. WHEN процесс экспортируется THEN система SHALL включить метаданные (версия, автор, дата создания, описание)

### Requirement 23

**User Story:** Как пользователь, я хочу иметь примеры и документацию, чтобы быстро начать работу с инструментом.

#### Acceptance Criteria

1. WHEN пользователь устанавливает систему THEN система SHALL включать примеры конфигураций для популярных сценариев
2. WHERE пользователь запрашивает помощь THEN система SHALL предоставить встроенную документацию по командам
3. WHEN пользователь изучает примеры THEN система SHALL предоставить рабочие конфигурации для dual-design и других процессов
4. WHERE документация описывает DSL THEN система SHALL включать полную спецификацию синтаксиса с примерами
5. WHEN пользователь создает первый процесс THEN система SHALL предложить интерактивный мастер настройки
