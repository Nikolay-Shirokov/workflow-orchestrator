# Requirements Document: Исправление передачи контекста между шагами

## Introduction

Система оркестрации workflow должна корректно передавать контекст (данные и артефакты) между шагами процесса. Текущая реализация имеет проблемы с обработкой вложенных подстановок переменных в шаблонах промптов, что приводит к тому, что содержимое артефактов не загружается в промпты.

## Glossary

- **Workflow**: Рабочий процесс, состоящий из последовательности шагов
- **Step**: Отдельный шаг в рабочем процессе
- **Artifact**: Файл, созданный в результате выполнения шага
- **Context**: Набор переменных и данных, доступных для использования в шагах
- **Template_Engine**: Компонент, отвечающий за подстановку переменных в шаблоны
- **Output**: Результат выполнения шага, который добавляется в контекст
- **Prompt**: Текст запроса, отправляемый в AI-модель

## Requirements

### Requirement 1: Корректная обработка вложенных подстановок

**User Story:** Как разработчик workflow, я хочу использовать вложенные подстановки переменных в шаблонах, чтобы динамически загружать содержимое артефактов.

#### Acceptance Criteria

1. WHEN шаблон содержит выражение `${artifact:${variable_name}}`, THE Template_Engine SHALL сначала разрешить внутреннюю переменную `${variable_name}` в путь к файлу
2. WHEN внутренняя переменная разрешена в путь, THE Template_Engine SHALL загрузить содержимое файла по этому пути
3. WHEN путь к файлу не существует, THE Template_Engine SHALL выбросить понятную ошибку с указанием отсутствующего файла
4. WHEN переменная не определена в контексте, THE Template_Engine SHALL выбросить понятную ошибку с указанием неопределенной переменной
5. THE Template_Engine SHALL поддерживать до 10 уровней вложенности переменных

### Requirement 2: Двойная передача контекста (содержимое + путь)

**User Story:** Как разработчик workflow, я хочу иметь доступ как к содержимому артефакта, так и к пути к файлу, чтобы выбирать оптимальный способ передачи данных.

#### Acceptance Criteria

1. WHEN шаг создает артефакт с именем `output_name`, THE System SHALL добавить в контекст переменную `output_name` с содержимым артефакта
2. WHEN шаг создает артефакт с именем `output_name`, THE System SHALL добавить в контекст переменную `output_name_file` с путем к файлу артефакта
3. THE System SHALL сохранять оба значения (содержимое и путь) в контексте одновременно
4. WHEN используется `${output_name}`, THE Template_Engine SHALL подставить содержимое артефакта напрямую
5. WHEN используется `${artifact:${output_name_file}}`, THE Template_Engine SHALL загрузить содержимое из файла по пути

### Requirement 3: Оптимизация передачи данных

**User Story:** Как разработчик workflow, я хочу минимизировать количество операций чтения файлов, чтобы улучшить производительность.

#### Acceptance Criteria

1. WHEN содержимое артефакта уже доступно в контексте, THE System SHALL использовать его напрямую без чтения файла
2. WHEN содержимое артефакта загружается из файла, THE Template_Engine SHALL кэшировать его на 5 минут
3. WHEN один и тот же артефакт используется в нескольких местах шаблона, THE Template_Engine SHALL загрузить его только один раз
4. THE Template_Engine SHALL логировать количество операций чтения файлов для мониторинга производительности

### Requirement 4: Обрамление вложенного контекста тегами

**User Story:** Как разработчик промптов, я хочу обрамлять вложенный контекст в парные теги, чтобы AI-модель могла четко различать границы вложенных данных.

#### Acceptance Criteria

1. WHEN в шаблоне промпта используется синтаксис `${artifact:${variable}:tag_name}`, THE Template_Engine SHALL обрамить содержимое артефакта в теги `<tag_name>` и `</tag_name>`
2. WHEN имя тега не указано, THE Template_Engine SHALL использовать имя переменной в качестве тега по умолчанию
3. WHEN содержимое артефакта пустое, THE Template_Engine SHALL все равно создать парные теги с пустым содержимым
4. THE Template_Engine SHALL экранировать специальные символы в именах тегов
5. WHEN используется синтаксис без тега `${artifact:${variable}}`, THE Template_Engine SHALL вставить содержимое без обрамления

### Requirement 5: Улучшенная диагностика ошибок

**User Story:** Как разработчик workflow, я хочу получать понятные сообщения об ошибках, чтобы быстро находить и исправлять проблемы в шаблонах.

#### Acceptance Criteria

1. WHEN переменная не определена, THE Template_Engine SHALL указать имя переменной и список доступных переменных
2. WHEN файл артефакта не найден, THE Template_Engine SHALL указать путь к файлу и шаг, который должен был его создать
3. WHEN превышен лимит итераций, THE Template_Engine SHALL показать цепочку вложенных переменных
4. WHEN происходит ошибка чтения файла, THE Template_Engine SHALL указать причину ошибки (права доступа, кодировка и т.д.)
5. THE Template_Engine SHALL логировать все попытки разрешения переменных на уровне DEBUG

### Requirement 6: Обратная совместимость

**User Story:** Как пользователь существующих workflow, я хочу, чтобы мои текущие конфигурации продолжали работать после обновления, чтобы не тратить время на миграцию.

#### Acceptance Criteria

1. THE System SHALL поддерживать существующий синтаксис `${variable}` для простых переменных
2. THE System SHALL поддерживать существующий синтаксис `${artifact:path/to/file}` для прямых путей
3. THE System SHALL поддерживать существующий синтаксис `${if:condition:then:else}` для условных блоков
4. WHEN используется старый синтаксис, THE System SHALL работать без изменений
5. THE System SHALL не требовать изменений в существующих конфигурациях workflow

### Requirement 7: Документация и примеры

**User Story:** Как новый пользователь системы, я хочу иметь понятную документацию с примерами, чтобы быстро научиться использовать систему.

#### Acceptance Criteria

1. THE Documentation SHALL содержать примеры использования `${artifact:${variable}}`
2. THE Documentation SHALL содержать примеры использования тегов `${artifact:${variable}:tag_name}`
3. THE Documentation SHALL объяснять разницу между `${variable}` и `${artifact:${variable_file}}`
4. THE Documentation SHALL содержать рекомендации по выбору способа передачи данных
5. THE Documentation SHALL содержать примеры обработки ошибок
