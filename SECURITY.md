## Сообщение об уязвимостях

Мы серьезно относимся к безопасности workflow-orchestrator. Если вы обнаружили уязвимость, пожалуйста, сообщите нам об этом ответственно.

### Как сообщить

**НЕ создавайте публичный issue для уязвимостей безопасности.**

Вместо этого:

1. **Отправьте email** на: [ваш-email@example.com] (замените на реальный)
   - Тема: `[SECURITY] Описание уязвимости`
   - Включите детальное описание проблемы
   - Шаги для воспроизведения
   - Потенциальное влияние
   - Предлагаемое решение (если есть)

2. **Используйте GitHub Security Advisories**:
   - Перейдите на https://github.com/Nikolay-Shirokov/workflow-orchestrator/security/advisories
   - Нажмите "Report a vulnerability"
   - Заполните форму

### Что включить в отчет

Пожалуйста, предоставьте:

- **Описание уязвимости**: Что именно уязвимо?
- **Тип уязвимости**: Injection, XSS, CSRF, и т.д.
- **Затронутые версии**: Какие версии подвержены?
- **Шаги воспроизведения**: Как воспроизвести проблему?
- **Proof of Concept**: Код или конфигурация для демонстрации
- **Влияние**: Какой ущерб может быть нанесен?
- **Предлагаемое решение**: Как это можно исправить?
- **Ваши контакты**: Для дальнейшей связи

### Процесс обработки

1. **Подтверждение** (в течение 48 часов):
   - Мы подтвердим получение вашего отчета
   - Присвоим уникальный идентификатор

2. **Оценка** (в течение 7 дней):
   - Проверим и воспроизведем уязвимость
   - Оценим серьезность (Critical, High, Medium, Low)
   - Определим затронутые версии

3. **Разработка исправления** (зависит от серьезности):
   - Critical: в течение 24-48 часов
   - High: в течение 7 дней
   - Medium: в течение 30 дней
   - Low: в следующем релизе

4. **Публикация**:
   - Выпустим патч
   - Опубликуем Security Advisory
   - Упомянем вас в благодарностях (если вы согласны)

### Координированное раскрытие

Мы просим вас:

- Дать нам разумное время для исправления (обычно 90 дней)
- Не раскрывать уязвимость публично до выхода патча
- Не эксплуатировать уязвимость за пределами необходимого для демонстрации

Мы обязуемся:

- Держать вас в курсе прогресса
- Упомянуть вас в благодарностях (если вы согласны)
- Выпустить патч как можно скорее

## Рекомендации по безопасности

### Для пользователей

1. **API ключи**:
   - Никогда не коммитьте API ключи в git
   - Используйте переменные окружения
   - Используйте `.env` файлы (добавьте в `.gitignore`)
   - Регулярно ротируйте ключи

2. **Конфигурации**:
   - Проверяйте конфигурации перед запуском
   - Используйте `dry-run` для валидации
   - Не запускайте недоверенные конфигурации
   - Ограничьте доступ к артефактам

3. **Плагины**:
   - Устанавливайте плагины только из доверенных источников
   - Проверяйте код плагинов перед использованием
   - Используйте изолированное окружение для тестирования

4. **Обновления**:
   - Регулярно обновляйте workflow-orchestrator
   - Следите за Security Advisories
   - Подпишитесь на уведомления о релизах

5. **Логи и артефакты**:
   - Не логируйте чувствительные данные
   - Ограничьте доступ к директории артефактов
   - Регулярно очищайте старые артефакты
   - Не публикуйте логи с секретами

### Для разработчиков плагинов

1. **Валидация входных данных**:
   - Всегда валидируйте пользовательский ввод
   - Используйте типизацию TypeScript
   - Проверяйте границы значений

2. **Выполнение команд**:
   - Избегайте `eval()` и подобных конструкций
   - Санитизируйте аргументы команд
   - Используйте параметризованные команды
   - Ограничьте доступ к файловой системе

3. **Зависимости**:
   - Минимизируйте зависимости
   - Используйте проверенные пакеты
   - Регулярно обновляйте зависимости
   - Проверяйте на уязвимости (`npm audit`)

4. **Секреты**:
   - Никогда не логируйте секреты
   - Используйте безопасное хранение
   - Очищайте секреты из памяти после использования

### Для мейнтейнеров

1. **Code Review**:
   - Проверяйте все PR на безопасность
   - Используйте автоматические сканеры
   - Требуйте тесты для новых функций

2. **Зависимости**:
   - Включите Dependabot
   - Регулярно обновляйте зависимости
   - Проверяйте `npm audit` перед релизом

3. **CI/CD**:
   - Запускайте тесты безопасности в CI
   - Используйте CodeQL или подобные инструменты
   - Проверяйте на известные уязвимости

4. **Релизы**:
   - Подписывайте релизы
   - Публикуйте checksums
   - Документируйте изменения безопасности
