# Руководство по вложенным подстановкам переменных

## Обзор

Workflow Orchestrator поддерживает вложенные подстановки переменных, позволяя динамически формировать пути к артефактам и создавать гибкие шаблоны промптов. Этот документ описывает синтаксис, примеры использования и лучшие практики.

## Что такое вложенные подстановки?

Вложенные подстановки - это возможность использовать переменные внутри других переменных. Это позволяет:

- Динамически формировать пути к файлам
- Создавать гибкие шаблоны промптов
- Переиспользовать общие паттерны
- Упрощать конфигурацию workflow

## Синтаксис

### Базовый синтаксис

```
${artifact:${variable_name}}
```

**Как работает:**
1. Сначала разрешается внутренняя переменная `${variable_name}`
2. Результат используется как путь к файлу
3. Содержимое файла загружается и подставляется в шаблон

### Синтаксис с тегами

```
${artifact:${variable_name}:tag_name}
```

**Как работает:**
1. Разрешается внутренняя переменная `${variable_name}`
2. Загружается содержимое файла по полученному пути
3. Содержимое обрамляется в теги `<tag_name>...</tag_name>`

## Примеры использования

### Пример 1: Простая вложенная подстановка

**Контекст:**
```json
{
  "analysis_file": "artifacts/session_123/analysis.md"
}
```

**Шаблон:**
```
Проанализируйте следующий документ:
${artifact:${analysis_file}}
```

**Результат:**
```
Проанализируйте следующий документ:
[содержимое файла artifacts/session_123/analysis.md]
```

### Пример 2: Вложенная подстановка с тегами

**Контекст:**
```json
{
  "research_file": "artifacts/session_123/research.md"
}
```

**Шаблон:**
```
Используйте результаты исследования:
${artifact:${research_file}:research_data}
```

**Результат:**
```
Используйте результаты исследования:
<research_data>
[содержимое файла artifacts/session_123/research.md]
</research_data>
```

### Пример 3: Множественные вложенные подстановки

**Контекст:**
```json
{
  "tech_analysis_file": "artifacts/session_123/tech.md",
  "biz_analysis_file": "artifacts/session_123/biz.md",
  "ux_analysis_file": "artifacts/session_123/ux.md"
}
```

**Шаблон:**
```
Объедините следующие анализы:

## Технический анализ
${artifact:${tech_analysis_file}:technical}

## Бизнес-анализ
${artifact:${biz_analysis_file}:business}

## UX анализ
${artifact:${ux_analysis_file}:user_experience}

Создайте единый документ требований.
```

**Результат:**
```
Объедините следующие анализы:

## Технический анализ
<technical>
[содержимое tech.md]
</technical>

## Бизнес-анализ
<business>
[содержимое biz.md]
</business>

## UX анализ
<user_experience>
[содержимое ux.md]
</user_experience>

Создайте единый документ требований.
```

### Пример 4: Динамическое формирование путей

**Контекст:**
```json
{
  "session_id": "session_123",
  "artifacts_dir": "artifacts",
  "step_name": "analysis"
}
```

**Шаблон:**
```
${artifact:${artifacts_dir}/${session_id}/${step_name}.md}
```

**Примечание:** Этот пример показывает концепцию, но текущая реализация требует, чтобы полный путь был в одной переменной.

## Двойная передача контекста

Система автоматически создает две переменные для каждого output:

1. **`output_name`** - содержимое артефакта (в памяти)
2. **`output_name_file`** - путь к файлу артефакта

### Пример использования двойной передачи

**Workflow конфигурация:**
```yaml
steps:
  - id: "analysis"
    type: "model"
    outputs:
      result: "${artifacts_dir}/analysis.md"
```

**Автоматически создаются переменные:**
```json
{
  "result": "[содержимое файла analysis.md]",
  "result_file": "artifacts/session_123/analysis.md"
}
```

**Использование в следующем шаге:**

```yaml
# Вариант 1: Прямое содержимое (быстрее)
prompt_template: |
  Используйте анализ:
  ${result}

# Вариант 2: Загрузка из файла (гарантия актуальности)
prompt_template: |
  Используйте анализ:
  ${artifact:${result_file}}

# Вариант 3: Загрузка с тегами (для больших данных)
prompt_template: |
  Используйте анализ:
  ${artifact:${result_file}:analysis_data}
```

## Глубина вложенности

Система поддерживает до **10 уровней вложенности** переменных.

### Пример многоуровневой вложенности

**Контекст:**
```json
{
  "env": "production",
  "production_dir": "artifacts/prod",
  "session_id": "session_123"
}
```

**Шаблон (концептуальный):**
```
${artifact:${${env}_dir}/${session_id}/result.md}
```

**Примечание:** На практике рекомендуется ограничиваться 2-3 уровнями вложенности для читаемости.

## Обработка ошибок

### Ошибка: Переменная не определена

**Шаблон:**
```
${artifact:${undefined_variable}}
```

**Ошибка:**
```
Error: Переменная не определена: undefined_variable
Доступные переменные: result, result_file, session_id, artifacts_dir
```

### Ошибка: Файл не найден

**Шаблон:**
```
${artifact:${missing_file}}
```

**Контекст:**
```json
{
  "missing_file": "artifacts/nonexistent.md"
}
```

**Ошибка:**
```
Error: Артефакт не найден: artifacts/nonexistent.md
Ожидалось создание в шаге: step_analysis
Проверьте, что предыдущий шаг успешно завершился
```

### Ошибка: Превышен лимит итераций

**Шаблон (циклическая зависимость):**
```
${artifact:${${${${${${${${${${${var}}}}}}}}}}}}
```

**Ошибка:**
```
Error: Превышен лимит итераций (10)
Возможна циклическая зависимость в переменных
Цепочка: var -> var -> var -> ...
```

## Производительность

### Сравнение подходов

| Подход | Первая загрузка | Повторная загрузка | Использование памяти |
|--------|-----------------|-------------------|---------------------|
| Прямое содержимое | ~1мс | ~1мс | Высокое |
| Вложенная подстановка | ~50мс | ~10мс (кэш) | Низкое |
| С тегами | ~52мс | ~12мс (кэш) | Низкое |

### Кэширование

- Артефакты кэшируются на **5 минут**
- Кэш автоматически инвалидируется при изменении файла
- Повторная загрузка использует кэш (ускорение в ~5 раз)

### Рекомендации по производительности

1. **Используйте прямое содержимое для outputs шагов:**
   ```yaml
   prompt_template: |
     ${result}  # Быстрее, чем ${artifact:${result_file}}
   ```

2. **Используйте вложенные подстановки для внешних файлов:**
   ```yaml
   prompt_template: |
     ${artifact:${external_file}}  # Гарантия актуальности
   ```

3. **Полагайтесь на кэширование для повторных загрузок:**
   - Первая загрузка: ~50мс
   - Повторная загрузка: ~10мс

## Лучшие практики

### ✅ Рекомендуется

```yaml
# 1. Используйте прямое содержимое для outputs
prompt_template: |
  ${analysis}

# 2. Используйте теги для больших данных
prompt_template: |
  ${artifact:${large_file}:data}

# 3. Используйте осмысленные имена переменных
outputs:
  technical_analysis: "${artifacts_dir}/tech.md"
  business_analysis: "${artifacts_dir}/biz.md"

# 4. Группируйте связанные данные
prompt_template: |
  ## Технический анализ
  ${technical_analysis}
  
  ## Бизнес-анализ
  ${business_analysis}
```

### ❌ Не рекомендуется

```yaml
# 1. Избыточная вложенность
prompt_template: |
  ${artifact:${artifact:${file}}}  # Слишком сложно

# 2. Неосмысленные имена
outputs:
  out1: "${artifacts_dir}/file1.md"
  out2: "${artifacts_dir}/file2.md"

# 3. Смешивание подходов без причины
prompt_template: |
  ${result}  # Прямое содержимое
  ${artifact:${result_file}}  # То же самое, но медленнее

# 4. Игнорирование тегов для больших данных
prompt_template: |
  ${artifact:${huge_file}}  # Без тегов сложно для AI
```


## Миграция с прямых путей

### Старый подход (прямые пути)

```yaml
prompt_template: |
  ${artifact:artifacts/session_123/analysis.md}
```

**Проблемы:**
- Жестко заданный путь
- Не работает с разными сессиями
- Сложно переиспользовать

### Новый подход (вложенные подстановки)

```yaml
prompt_template: |
  ${artifact:${analysis_file}}
```

**Преимущества:**
- Динамический путь
- Работает с любой сессией
- Легко переиспользовать

### Рекомендуемый подход (прямое содержимое)

```yaml
prompt_template: |
  ${analysis}
```

**Преимущества:**
- Самый быстрый
- Простой синтаксис
- Минимум операций I/O

## Интеграция с другими функциями

### Условные блоки

```yaml
prompt_template: |
  ${if:research_available:${artifact:${research_file}:research}:Исследование не проводилось}
```

### Параллельные шаги

```yaml
steps:
  - id: "parallel_analysis"
    type: "parallel"
    steps:
      - id: "tech"
        outputs:
          tech: "${artifacts_dir}/tech.md"
      - id: "biz"
        outputs:
          biz: "${artifacts_dir}/biz.md"
  
  - id: "merge"
    depends_on: ["parallel_analysis"]
    prompt_template: |
      ${artifact:${tech_file}:technical}
      ${artifact:${biz_file}:business}
```

## Часто задаваемые вопросы

**Q: Какая максимальная глубина вложенности?**
A: 10 уровней, но рекомендуется не более 2-3 для читаемости.

**Q: Работает ли кэширование для вложенных подстановок?**
A: Да, артефакты кэшируются на 5 минут независимо от способа загрузки.

**Q: Можно ли использовать вложенные подстановки в путях outputs?**
A: Да, но путь должен быть полностью разрешен до сохранения артефакта.

**Q: Что быстрее: прямое содержимое или вложенная подстановка?**
A: Прямое содержимое (~1мс) быстрее вложенной подстановки (~10-50мс).

**Q: Когда использовать теги?**
A: Для больших данных (> 1000 символов) или множественных артефактов в одном промпте.

**Q: Как отладить проблемы с вложенными подстановками?**
A: Включите DEBUG логирование и используйте dry-run режим.

**Q: Можно ли комбинировать разные подходы?**
A: Да! Используйте прямое содержимое для небольших данных и вложенные подстановки с тегами для больших.

**Q: Что делать при ошибке "Переменная не определена"?**
A: Проверьте, что предыдущий шаг создал output с нужным именем и успешно завершился.
